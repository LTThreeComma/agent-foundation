# Transition: from the old package to this one

There is no old-to-new data migration. Move the old implementation to legacy, build the new Service under its final name, and validate the new behavior before switching deployments. Legacy is a source reference, not a runtime dependency or a required regression suite.

## Package placement and build boundary

| Identity                     | Legacy reference               | New implementation      |
| ---------------------------- | ------------------------------ | ----------------------- |
| Package directory            | `packages/a13n-service-legacy` | `packages/a13n-service` |
| Specification directory      | `spec/a13n-service-legacy`     | `spec/a13n-service`     |
| User documentation directory | `docs/a13n-service-legacy`     | `docs/a13n-service`     |
| Exported contract directory  | `proto/a13n-service-legacy`    | `proto/a13n-service`    |
| Distribution                 | `a13n-service-legacy`          | `a13n-service`          |
| Python package               | `a13n_service_legacy`          | `a13n_service`          |
| Command                      | `a13n-service-legacy`          | `a13n-service`          |

Move the four old Service directories above before building their replacements in the canonical paths. The old package carries its migrations, package tests and README with it; they need no separate legacy directories. Rename its import namespace and package/entry-point metadata before creating the new canonical package. Do not add an `a13n_service` compatibility alias that resolves to legacy. Legacy tests are neither ported nor repaired as part of this move. Keeping a working legacy build, command or test suite is not a rewrite gate; rollback uses the previously built deployment, not a rebuilt legacy checkout.

Move the old `spec/a13n-service/` to `spec/a13n-service-legacy/` alongside the source move and mark it as historical reference, not the new Service contract. Create and maintain new specifications at `spec/a13n-service/` from this design as implementation proceeds; do not leave superseded requirements in the canonical directory. Update specification indexes, agent reading instructions and current documentation links to the new contract. Links intentionally citing old behavior must identify and point to legacy instead of silently resolving to the new specification. Shared-library and repository engineering specifications retain their own authority. Update superseded Service rules in shared documents, such as `spec/frontend/console.md`, in place; do not archive whole shared specification directories.

Archive old user documentation under `docs/a13n-service-legacy/` and old exported contracts under `proto/a13n-service-legacy/`, with both clearly marked as historical reference. Write current user documentation at `docs/a13n-service/` and regenerate current contract exports at `proto/a13n-service/` from the new implementation. The contract includes the supported event schemas and wire fixtures as well as OpenAPI; update these together instead of retaining old non-HTTP contracts beside a new HTTP export. Current site navigation, generated references and Console generation must use only new content; links intentionally citing history must explicitly point to legacy.

Exclude legacy from default workspace installation, validation, test discovery, build and release. Check workspace globs and discovery rules explicitly: renaming a directory does not exclude it automatically. Update workspace selection, package/type-check paths, test launchers and impact maps, Make targets, development launchers, container inputs, CI filters/jobs, contract export and release selection so each canonical Service target addresses only the new implementation. Preserving shared Harness/library checks does not re-enable legacy checks. New code and fixtures must not import legacy business modules or depend on its migrations/configuration. Reuse the Harness and shared libraries through their supported interfaces.

Update or replace `dev/live_tests`, `dev/service`, deployment configuration, Make targets and CI in place for the new Service; do not create parallel legacy toolchains. Adapt `frontend/apps/a13n-console` in place and regenerate its client types from the new contract. Update contract/documentation generators, checks and path filters together, including their schema and configuration inputs. Establish this routing at the start so an unfinished new path fails clearly instead of consuming legacy code or snapshots; complete each replacement as its new implementation becomes available.

The new package has its own initial migrations and configuration. Generate migrations through the implementation repository's supported workflow. Use separate PostgreSQL databases, Redis prefixes and object namespaces from any old deployment; never point a new migration or test at an old store. Package renaming is a repository change, not a production cutover. Build/test commands must expose incomplete new implementation honestly, rather than forwarding to legacy for a successful result.

## What has no successor

Anyone relying on these must be told before the switch:

- A2A endpoints and agent cards.

- Hosted AG-UI endpoint (`/ag-ui/v1`).

- Agent-scoped role bindings.

- Configuration drafts, draft APIs, verification runs.

- Live mounts into a running run.

- Bot application and platform-specific integrations; the excluded scope is defined in [01](01-goals.md#what-leaves-the-service). No `apps/bot` is built or required for acceptance.

- WebSocket envd ingress, device pairing, connection tickets, presence, reconnect takeover and relay: deferred; this iteration supports HTTP envd only.

- Inline hook subscriptions and hook subscription revisions; Item-level and environment hook events.

- Queue edits tied to `queue_version`; replaced by pending-only edits with thread ETags.

- The retry endpoint: resubmit the input instead; failed runs never become head.

- Destructive interactive thread/asset deletion: archive/retirement preserves retained facts.

- A plain shared Redis cursor: clients implement attempt segments and reset control frames.

- Agent memory in any form: providers, entries, subjects, organization.

- Run priorities and named queues.

## Sequence and switch gates

1. Archive the four old Service directories and establish canonical paths, build/test isolation and documentation/contract routing above. Create new test fixtures and replace live-test launch/discovery configuration; no step requires a passing legacy suite.
2. Build the execution spine with a deterministic model through the real Harness and one supported provider: bootstrap, configure, submit, claim, checkpoint, display, seal, observe. Exercise crash cuts and two-worker contention before expanding resources. This is the first milestone, not completion of the rewrite.
3. Add input editing, waiting feedback, fork and child delivery. Run the schedules in [12-validation.md](12-validation.md), including stale authority and final-boundary races.
4. Prove real Harness incorporation/compaction and display recovery, transactional event cursors, Redis loss/backpressure, conditional snapshot replacement, two-object display/checkpoint ordering, and receipt confirmation racing recovery or terminal seal. Object reclamation is out of scope.
5. Implement the remaining in-scope management and provider capabilities. Prove managed environment operations, connect-only HTTP envd and rotating OAuth with fault injection, including remote success followed by lost database commit. Qualify each advertised provider separately; no WebSocket envd or Bot capability is required.
6. Integrate Console and public submission, observation, feedback and MCP journeys as soon as their Service paths work; do not postpone all consumer feedback until the end. Verify the #411 distribution and #410 fake-budget fixtures. Complete Console's in-scope flows and the new live suite; a minimal UI or one successful request is only a milestone.
7. Meet [12's completion criteria](12-validation.md#implementation-acceptance-record), including representative load measurements, build/deployment checks and current contracts/documentation. Record any separately owned consumer work before scheduling a deployment switch.

New package tests and the rewritten `dev/live_tests` validate these stages. Test ownership, execution evidence and the distinction between a stage and complete delivery belong to [12](12-validation.md); they are not inferred from the number of migrated files or closed review comments. This design repository itself contains no Service implementation or migration.

There is no live data migration. Switching requires an explicit destination environment, consumer rollout and decision about historical access to the old deployment. Rollback returns consumers to that old deployment; it does not imply new-format runs are readable by old code. Preserve old stores until the retention/rollback window is agreed.

Record the design revision and implementation-repository revision at handoff. Old-code citations describe their named historical revisions; verify relevant code against the actual source before relying on it. Later legacy changes are reference material to assess against the current scope, not an automatic porting backlog. Removing old forwarding types alone does not prove that the guarantees they carried survived; the new tests must demonstrate the current design's guarantees.
